# 10. HR-аналитика, помощь и личные награды

> Статус: проектные материалы. Фактический запуск и результаты текущей реализации см. в [README](../README.md), [ACCEPTANCE](ACCEPTANCE.md), [FORMULAS](FORMULAS.md) и [DEMO_API](DEMO_API.md). Непроверенные положения ниже не являются заявлением о готовности.

Основание: [S-FINAL §§13–14, S-TZ](SOURCES.md).

## 1. Общие правила аналитики

Каждый показатель ограничен workspace/tenant, ролью, выбранным периодом и датой анализа. Каждый процент показывает numerator/denominator. Если denominator=0, результат null/«нет данных».

Общая статистика текущих role requirements и статистика по карьерной цели — разные срезы. Основные формулы S-FINAL ниже относятся к указанной цели; при добавлении current-role view его явно подписать и не смешивать знаменатели.

## 2. Формулы

| Показатель | Определение и важное условие |
|---|---|
| Частота gap навыка s | Число сотрудников с gap_s>0 / число сотрудников с целью, требующей s. |
| Средний gap навыка s | Сумма gap_s / число сотрудников, которым s требуется; закрывшие включаются с gap=0. |
| Critical gaps | Число сотрудников с незакрытым критическим навыком. Не индивидуальный рейтинг. |
| Завершаемость когорты | completed / все включённые записи когорты; рядом распределение остальных statuses. |
| No-show | no_show / записи состоявшихся scheduled sessions со статусами completed, in_progress, dropped, no_show. |
| Просрочка mandatory | mandatory && status!=completed && due_date < as_of. Нет due_date — не выдумывать overdue. |
| Нет следующего шага | Цель определена, есть gap, нет доступного полезного нового/продолжаемого шага. |
| Нет completed добровольного развития 90 дней | Стаж не менее 90 дней и нет соответствующего completed за период. Не прогноз оттока. |
| Нагрузка | Запланированные часы недели / согласованный бюджет недели. |
| Возраст открытой заявки | REAL_NOW − submitted_at; единицы указаны. |
| Время решения | decided_at − submitted_at по завершённым решениям; медиана и n. |
| Catalog gap | Есть спрос на skill, но нет подходящего достижимого покрытия; учитывать пределы поиска. |
| Возможная группа на событие | Число уникальных сотрудников, которым оно допустимо и полезно. Не дублировать человека по нескольким skills. |

Для «стаж >=90 дней» использовать hire_date и выбранную дату, а не неявно заменять 90 дней тремя календарными месяцами. Для недельной нагрузки нужны фактические plan schedule/budget; общая длительность курса сама по себе не распределяет часы по неделям.

## 3. Временные ограничения

У self-paced историческое `date` — зачисление/назначение. Поэтому периодный показатель по нему является когортой зачисления, а не точным временным рядом завершений. Proxy-дату можно использовать согласно политике, но её качество отмечается.

Будущие sessions не считать состоявшимися. Точный on-time показатель разрешён только для достоверных дат:

```text
OnTimeRate = count(completed_at <= due_date) /
             count(завершённых с обеими достоверными датами)
```

Не подменять его долей «закрыто сейчас среди уже наступивших назначений». В исходном наборе нет цен и реального бюджета обучения: ROI/финансовую экономию банка не считать. Будущий пилот может измерить эффект, синтетическая демонстрация его не доказывает.

## 4. Причины отсутствия шага

S-FINAL перечисляет `goal_missing`, `goal_skills_met`, `prerequisites_blocked`, `audience_blocked`, `no_session`, `catalog_gap`, `awaiting_approval`.

**В источнике есть неоднозначность:** определение метрики требует известной цели и открытого gap, но перечень причин содержит `goal_missing` и `goal_skills_met`. Предлагаемое уточнение S-DESIGN — трактовать список как общий каталог состояний профиля, а эти две группы показывать отдельно от numerator «нет следующего шага». Это не молчаливое изменение исходника: трактовку должна явно закрепить команда (CQ-OPEN-09).

Если причин несколько, либо выбрать документированную primary reason, либо честно показать multiple labels без суммы процентов «100%». Конкретный приоритет primary reason не задан S-FINAL — требуется решение реализации.

Ошибка AI — технический статус. Catalog gap нельзя ставить только потому, что provider не ответил или bounded search достиг лимита.

## 5. Поясняющий пример метрик

Четырём сотрудникам нужен skill s, их gaps: 2, 0, 1, 0. Частота gap=2/4=50%; средний gap=3/4=0.75. Сотрудник, чья цель s не требует, не добавляется в знаменатель.

Когорта из десяти записей с семью completed даёт 7/10=70%, но остальные три должны быть показаны по статусам. Если одна из записей ещё in_progress, показатель не превращается автоматически в оценку качества сотрудника или курса.

## 6. Помощь и обязательные назначения

Польза назначения объясняется отдельно от развития к цели. Для mandatory показывать фактический дедлайн, статус и обращение за помощью. Нет фиктивного gain у комплаенса; onboarding с effects обрабатывается по своему каталогу.

Сотрудник добровольно выбирает причину затруднения. Менеджер может согласовать время/ресурс, HR — предложить допустимый формат. Обязательную программу нельзя отменить одним «материал знаком». In-app reminders основаны на реальных назначениях; не заявлять отправку email/мессенджерных уведомлений без реализованной интеграции.

## 7. XP: проектная формула S-FINAL

```text
XP_completion = 20 за одно подтверждённое уникальное завершение
XP_skill = 15 * число новых впервые подтверждённых границ уровней навыков
XP_total_credit = XP_completion + XP_skill
SpendableBalance = sum(active_credits) - sum(active_debits)
PersonalLevel = 1 + floor(net_lifetime_earned_XP / 100)
```

Границы уровней награждаются выше lifetime baseline/max уже подтверждённого. Смена цели и повторная аттестация не создают те же XP заново. Baseline/эффективные навыки и lifetime threshold accounting должны быть согласованы.

Для historical seed S-FINAL допускает два варианта: воспроизвести согласованную reward ledger истории либо начать lifetime baseline с импортированного effective state. **Выбранный вариант пока не установлен** — указать его в релизной policy. Не начислять награду за все существующие навыки при каждом запуске/импорте.

Пример для добровольного уникального завершения: две новые подтверждённые skill boundaries дают 20 + 2×15 = 50 XP. Если границы уже награждены ранее, skill XP за них не повторяется. Approved proposal без принятого результата даёт 0.

## 8. Неразрешённый конфликт обязательных XP

S-FINAL §13 прямо допускает completion XP за комплаенс без skill XP. При этом S-TZ запрещает игровую механику вокруг обязательных процессов, приводя пример очков за таймшиты.

**В этом комплекте правило не изменено молча и соответствие не объявлено.** Это открытый вопрос CQ-OPEN-01: команда должна получить/зафиксировать применимую трактовку и утвердить соответствующую политику до заявления о готовности. До решения нельзя отмечать compliance rewards как прошедшие проверку соответствия ТЗ. См. [реестр решений](15_RELEASE_AND_LIMITATIONS.md).

Независимо от решения, обязательные назначения остаются отдельной дорожкой; отсутствие skill effects не заполняется выдуманным приростом.

## 9. Ledger и обмен

Redemption — атомарный debit при достаточном балансе, с uniqueness/idempotency. Недостаточный баланс → отказ без отрицательного значения. Личный уровень не уменьшается от траты: он основан на earned XP, а не spendable balance.

Повтор accepted/completion/request не создаёт новую награду. EV_036 награждается лишь за подтверждённую уникальную реальную сессию, не за бесконечные самостоятельно созданные участия.

Отмена ошибочного начисления при уже потраченной награде создаёт audit/review case, а не скрывает расхождение. Решение не записывается удалением прежнего debit.

Каталог демо — пример политики: менторская сессия, согласованное время на проект, признание milestone. Это не обещание реальных призов/денег от Halyk. Публичный рейтинг людей отсутствует; допустимы личные milestones и командные агрегаты без ranking.

Проверки: T10, T11, T14, T17. Проверка mandatory rewards отдельно ожидает решения CQ-OPEN-01.
