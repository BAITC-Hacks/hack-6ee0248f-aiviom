# 04. Единый расчётный модуль

Основание: [S-FINAL §10](SOURCES.md). Формулы ниже — проектная политика AIVIOM, а не правила кадровой аттестации Halyk. Все приведённые числовые мини-примеры — поясняющие синтетические примеры.

## 1. Общие требования

Вычислять на сервере либо в едином общем domain-модуле. UI получает готовые значения. LLM не является источником арифметики. Уровни навыков порядковые: сумма уровней — условный продуктовый индикатор, не измерение ценности человека.

Отсутствующий skill в baseline имеет значение 0. Неразрешённая цель отличается от цели, все требования которой уже выполнены. `null` для неопределённой метрики не заменять 0 или 100.

## 2. Skill gain и cap

Для текущего уровня `x`, прироста `g` и cap `m`:

```text
delta = max(0, min(g, m - x, 5 - x))
new_x = x + delta
```

Ограничения входа: `0 <= x <= 5`, `g >= 0`, `0 <= m <= 5`. Невалидный вход отклоняется; он не исправляется незаметным clamp в импортере.

| x | g | m | delta | new_x | Что проверяет |
|---:|---:|---:|---:|---:|---|
| 2 | 1 | 4 | 1 | 3 | Обычный прирост. |
| 2 | 2 | 3 | 1 | 3 | Ограничение прироста cap. |
| 3 | 1 | 3 | 0 | 3 | Потолок достигнут. |
| 4 | 1 | 3 | 0 | 4 | Низкий cap не понижает навык. |
| 5 | 2 | 5 | 0 | 5 | Общий максимум шкалы. |

Фраза «не выше cap» ограничивает новое начисление; она **не** требует понизить уже существующий уровень выше cap.

Gain применяется только для подтверждённого completed либо accepted credit. `completion_pct=80` не даёт 80% gain. Нельзя самостоятельно отменить completed из-за низкого score: такого порога нет в источнике.

## 3. Восстановление актуального состояния

```text
state = копия review baseline
records = активные учитываемые завершения/credits
records = completed после last_review_date
sort records by (effective_completed_at, stable_record_id)
for record in records:
    for effect in зафиксированных эффектах record:
        state[skill] = apply_gain(state[skill], effect)
```

Исторические записи используют документированный proxy `date`, если нет completed_at. Новые credits используют доменный timestamp. Completion ровно на review date повторно не начисляется.

Результат содержит provenance: baseline version, учтённые record/credit IDs, timing quality, использованную версию catalog/policy. Как хранить snapshot эффекта исторического события при изменении каталога — зафиксировать в actual schema; нельзя незаметно пересчитать историю по новой неподтверждённой политике.

### Почему отмена требует replay

Baseline `x=1`. Результат A: gain 2, cap 3 → `x=3`. Результат B: gain 2, cap 4 → `x=4`.

При отмене A правильный replay только B от baseline даёт `x=3`. Простое `4 - 2 = 2` неверно. Поэтому отмена помечает credit неактивным и пересчитывает весь соответствующий state от baseline.

## 4. Цель и разрывы

Приоритет определения цели: явный `career_goal` → предложенный следующий грейд той же роли. Предложенная цель должна быть обозначена как предложенная. Для Lead без цели не создавать следующий грейд.

Для множества требуемых навыков `S`, где `r_s > 0`:

```text
gap_s = max(0, r_s - x_s)
D = sum(gap_s)
Coverage = 100 * sum(min(x_s, r_s)) / sum(r_s)
CriticalMet = count(s in critical_skills where x_s >= r_s)
```

`Coverage` — **невзвешенная** формула S-FINAL. CriticalMet показывается отдельно как `закрыто / всего критических`. Критичность влияет на ранжирование, но не добавляет неоговорённый вес в Coverage.

Если цели нет, пары role/grade нет либо нет определённых требований, Coverage=null и понятное состояние «нет цели/данных». Полное соответствие означает выполнение **всех** required skills, не только критических.

### Мини-пример

Требования: System Design 4, API Design 3. Текущие уровни: 2 и 2.

```text
gaps = 2 + 1 = 3
Coverage = 100 * (2 + 2) / (4 + 3) ≈ 57.14%
```

После эффекта +1 к System Design и +1 к API Design, с подходящими caps:

```text
new levels = 3, 3
new gaps = 1 + 0 = 1
new Coverage = 100 * 6 / 7 ≈ 85.71%
PreviewImpact_pp ≈ 28.57 процентного пункта
```

Это не вероятность повышения. Округление для UI не должно менять проверку prerequisites; фактическую точность отображения фиксирует frontend contract.

## 5. Прогресс от начала плана

При создании версии плана сохранить исходный gap `D0`:

```text
Progress = 100 * clamp((D0 - D) / D0, 0, 1), если D0 > 0
```

В мини-примере при D0=3 и D=1 Progress≈66.67%, тогда как Coverage≈85.71%. Эти показатели нельзя объединять или подменять друг другом.

Если D0=0: «на старте требования уже выполнены». Если корректировка данных увеличила gap до D>D0: показать предупреждение и действительный gap; нулевой clamp не должен скрыть ухудшение данных. Смена цели — новая baseline version; историю и награды не удалять.

## 6. Milestones, prerequisites и preview

```text
milestone_met = all(x_s >= threshold_s for s in milestone.conditions)
prerequisites_met = all(x_s >= prerequisite_e_s for s in event.prerequisites)
PreviewImpact_pp = Coverage(apply(event, copy(state))) - Coverage(state)
```

Альтернативные действия дают OR-пути к одной компетенции. Условия допуска отдельного события по умолчанию AND: требуется выполнить все prerequisites. Проектный target grade не заменяет фактический grade при проверке аудитории.

Preview использует копию state; не создаёт history, skill credits, XP или approval. Рекомендация модели и approval предложения не считаются доказательством навыка.

## 7. Часы, нагрузка и сроки

```text
PlanHours = sum(duration_hours активностей выбранного маршрута)
WeeksLowerBound = ceil(PlanHours / weekly_budget_hours), если budget > 0
SavedHours = BaselinePlanHours - AlternativePlanHours
LoadRatio = scheduled_hours_this_week / agreed_budget_hours_this_week
```

Без бюджета срок неизвестен. При нулевом бюджете не делить на 0. WeeksLowerBound — нижняя оценка по трудозатратам, без гарантии учёта расписаний и согласований; не выдавать её за точную дату.

Для PlanHours нужны известные трудозатраты выбранных действий. Если часть часов unknown, нельзя показывать неполную сумму как точное полное значение. Способ представления частичного результата — дополнительное UI/data решение, фиксируемое в реализации.

SavedHours допустим только для маршрутов, закрывающих одинаковые требования при сопоставимых условиях. Отрицательное значение подписывается как дополнительные часы. Уже затраченное время отделяется от оставшегося. Расчёт remaining_hours через completion_pct — оценка, а не точный факт.

Пример: два эквивалентных маршрута 12 и 8 часов при бюджете 4 часа/неделю дают экономию 4 часа и нижние оценки 3 и 2 недели. Фактическая более поздняя сессия может изменить реальный срок.

## 8. Инварианты для тестов

T06 проверяет cap и отсутствие gain у незавершённого. T07 — review cutoff. T10 — повторное выполнение и persistence. T12 — отсутствие мутации от preview. T16 — актуальность после изменения цели/истории. В каждой проверке сравнивать domain state, API и видимое значение UI, а не только формат ответа.
