## 3. Release gates

| Gate | Условие допуска |
|---|---|
| G1 — code provenance | Работа в официальном repo; история сохранена, выбран фактический commit. |
| G2 — data provenance | Разрешённая версия seed, checksum, wrappers и extensions описаны. |
| G3 — runtime | Фактические команды и зависимости; чистый старт и persistence проверены. |
| G4 — P0 main flow | Произвольный профиль, live AI, evidence, completion, HR и импорт работают. |
| G5 — access | Независимый judge path и server-side role/workspace scope проверены. |
| G6 — claims | README/FAQ соответствуют реализации; незавершённое явно помечено. |
| G7 — evidence | Tests/latency/clean-room связаны с tested commit; нет выдуманных PASS. |
| G8 — security/disclosure | Нет секретов, source/jury данных вне разрешённого scope; компоненты/лицензии раскрыты. |
| G9 — submission | Версия опубликована до установленного cutoff, платформа/приём проверены отдельно. |

Не все эти gates являются самостоятельными числовыми критериями жюри: это release checklist команды для выполнения исходных требований.

## 4. Перед публикацией

Проверить локальные изменения и подготовить обычный commit без переписывания прежней истории. Сверить SHA опубликованной ветки с тем, что реально тестировалось. Безопасные команды просмотра:

```bash
git status --short
git rev-parse HEAD
git ls-remote origin refs/heads/main
```

Если код менялся после tests, повторить затронутые проверки и обновить tested SHA. Не выдавать commit без push за удалённую публикацию. Не использовать force-push, удаление `.git`, подмену дат, reset истории или amend чужого стартового commit ради отчёта.

Согласно источнику, итоговый cutoff — 23.09.2026 18:00 Asia/Astana (UTC+05:00); новые коммиты после него не считаются автоматически оценочной версией. Часовые промежуточные результаты должны отражать реальный прогресс, а не искусственные исторические checkpoints.

Секреты не вставлять в карточку. Обращение к live demo и доступ к private repo проверяются из разрешённой независимой session, не только из браузера капитана.

## 6. Что не является доказательством готовности

Красивый UI без работающей мутации; fixture вместо нового AI inference; HTTP 200 вместо проверки правил; schema JSON вместо проверки фактов; local startup с untracked файлами; запуск только с личным API ключом капитана; скриншот вместо latency log; написанная документация вместо code tests.

## 7. Известные границы дизайна

Синтетический набор, proxy completion dates, порядковая шкала skills, bounded roadmap search, ручное человеческое принятие evidence, prototype demo identities, зависимость live AI от доступного сервиса, неустановленный эффект продукта на реальные бизнес-показатели. Эти границы остаются видимыми даже после успешной реализации.
