# 01. Продукт, требования и границы

> Статус: проектные материалы. Фактический запуск и результаты текущей реализации см. в [README](../README.md), [ACCEPTANCE](ACCEPTANCE.md), [FORMULAS](FORMULAS.md) и [DEMO_API](DEMO_API.md). Непроверенные положения ниже не являются заявлением о готовности.

Основание: [S-TZ, S-RULES, S-FINAL §§1–4](SOURCES.md).

## 1. Назначение

Career Quest должен сделать связь между деятельностью сотрудника и его развитием видимой: не просто напомнить о курсе, а показать, какую компетенцию он подтверждает, зачем она нужна выбранной цели и что станет доступно после результата.

Главная цепочка: профиль → актуальные навыки → gaps → допустимые шаги → объяснимая AI-рекомендация → подтверждение результата → пересчёт → новая траектория и управленческая аналитика.

Основной пользователь исходного ТЗ — сотрудник со стажем 1–5 лет. Это описание аудитории, а не запрет импортировать профиль с другим стажем. Второй основной пользователь — HR. Advisor, менеджер и супервайзер программы добавлены в согласованной продуктовой версии команды.

## 2. Обязательные требования P0

| ID | Требование | Наблюдаемое доказательство |
|---|---|---|
| CQ-P0-01 | Использовать фактический стартовый кит и сохранять его исходную семантику | Валидный seed; audit/import manifest; T01, T07. |
| CQ-P0-02 | Открывать произвольный профиль | Роль, грейд, стаж, навыки, история, цель и доступные следующие шаги; T02. |
| CQ-P0-03 | Выдавать 1–3 релевантных AI-рекомендации | Live response по проверенным кандидатам, без специальных employee IDs; T04. |
| CQ-P0-04 | Объяснять выбор минимум по трём факторам | Факты о грейде, gaps, истории и требованиях цели; отсутствующие данные явно отмечены; T04–T05. |
| CQ-P0-05 | Обновлять навыки и маршрут после выполнения | Gain/cap, уникальный зачёт, пересчёт и сохранение; T06–T10. |
| CQ-P0-06 | Показывать HR дефициты, отсутствие шага и участие | Формулы, numerator/denominator, drill-down в разрешённом scope; T14. |
| CQ-P0-07 | Принимать дополнительные профили/историю жюри | Preview, проверки, atomic import и свежая рекомендация; T03. |
| CQ-P0-08 | Разделять права сотрудника и HR | Проверки на сервере, включая обращения напрямую к API; T13. |
| CQ-P0-09 | Соблюдать время отклика | UI до 2 секунд, AI-рекомендация до 10 секунд; реальные измерения T18. |
| CQ-P0-10 | Обеспечить самостоятельный запуск | Чистая копия, seed, роли, main flow и независимый live AI; T19–T20. |

Если доступных кандидатов меньше трёх, вернуть имеющиеся. Если нет ни одного, вернуть осмысленный empty state с причинами, а не выдуманное мероприятие. Отдельный HR-сценарий «нет следующего шага» предусмотрен ТЗ.

## 3. Согласованное расширение P1

| ID | Возможность | Проверка |
|---|---|---|
| CQ-P1-01 | Пять ролей на общей инфраструктуре | Непустые role views и серверный scope. |
| CQ-P1-02 | Side quest с критериями, доказательствами и принятием | Approval без gain; accepted с одним credit; запрет self-approval. |
| CQ-P1-03 | Milestones и альтернативный маршрут | Компетенция может закрыть требование, но непройденный курс не становится completed. |
| CQ-P1-04 | Preview и сравнение альтернатив | Проверяемые before/after без записи в профиль. |
| CQ-P1-05 | Личная мотивация и награды | Прозрачные ledger, отсутствие рейтинга людей; конфликт обязательных XP разрешён. |
| CQ-P1-06 | Назначения, помощь, ресурсы | Отдельная обязательная дорожка, причины помощи, согласование времени. |
| CQ-P1-07 | Заполненные demo scenarios | Оригинальный seed отделён от маркированных extensions. |

P2: автоматический поиск учебных возможностей с источниками, расширенные фильтры, полная локализация, более богатый каталог наград. Учебные возможности за пределами каталога остаются частью развития сотрудников и проходят тот же внутренний процесс согласования.

## 4. Что не строим и не обещаем

Не требуются микросервисы, корпоративный SSO, воспроизведение курсов внутри приложения, полноценный чат, интеграции календаря/мессенджеров, платежи или прогноз оттока. Нельзя выдавать отсутствие готовых интеграций за их наличие.

Не обещаем повышение, доход, трудоустройство, доказанную экономию банка или рост завершаемости. Не повышаем фактический grade автоматически. Нет публичного рейтинга сотрудников, скрытой психологической оценки или использования реальных персональных данных.

Участие в добровольных активностях не должно превращаться в принуждение. Механики обязательных процессов рассматриваются отдельно; конфликт XP за комплаенс зафиксирован в [ограничениях релиза](15_RELEASE_AND_LIMITATIONS.md).

## 6. Прослеживаемость

Каждое требование должно иметь реализацию, путь проверки, результат и evidence для конкретного commit. Центральная таблица — [ACCEPTANCE](ACCEPTANCE.md). Информация о «написанной функции» без запуска соответствующего сценария не переводит её в PASS.
