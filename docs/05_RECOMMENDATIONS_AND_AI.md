# 05. Рекомендации, LLM и доказательства выбора

> Статус: проектные материалы. Фактический запуск и результаты текущей реализации см. в [README](../README.md), [ACCEPTANCE](ACCEPTANCE.md), [FORMULAS](FORMULAS.md) и [DEMO_API](DEMO_API.md). Непроверенные положения ниже не являются заявлением о готовности.

Основание: [S-FINAL §11, §§7, 12, 18](SOURCES.md).

## 1. Разделение решений

Детерминированный код отвечает за факты, gain/cap, prerequisites, аудиторию, повторное участие и расписание. LLM получает проверенные кандидаты, **действительно выбирает и сравнивает** следующие шаги, объясняет порядок и компромиссы. Модель не обязана повторять предварительный Priority, но не может нарушать hard eligibility.

Если модель лишь пишет текст под одним заранее окончательно выбранным мероприятием, это не соответствует согласованному дизайну §11.3. Если весь выбор делает модель без серверной проверки, не обеспечивается корректность правил.

## 2. Candidate builder

Вычислять отдельно:

| Пул | Назначение |
|---|---|
| Доступные новые добровольные события | Основные 1–3 каталожные рекомендации. |
| Полезные `in_progress` | Действие «продолжить», без повторной регистрации. |
| Заблокированные перспективные | Явный blocker и подготовительная цепочка. |
| Обязательные назначения | Отдельная HR-дорожка; не добровольные рекомендации. |
| Согласованные side quests | Дополнительный namespace и собственный workflow; не подмена каталожных IDs. |

Новые каталожные события проверяются по current role/grade, effective skills, prerequisites, повторности, наличию сессии и полезности для цели/достижимой цепочки. Уже completed не повторять, кроме уникальной следующей сессии EV_036. Self-paced доступен без upcoming date; online/offline требует доступной будущей сессии относительно выбранной доменной даты.

Точная граница «сессия сегодня доступна» должна быть единообразно закреплена в реализации и тесте: исходник содержит даты без времени. Не считать все прошедшие historical participations недействительными из-за отсутствия в сегодняшнем upcoming_sessions.

Remote — soft signal, а не автоматический запрет offline. Только явно известное ограничение может стать hard filter.

## 3. Прозрачные признаки

Для кандидата e:

```text
U_e = sum(min(gap_s, delta_e_s)) по навыкам цели
K_e = sum(min(gap_s, delta_e_s)) только по критическим навыкам
E_e = U_e / duration_hours_e, если duration_hours_e > 0
B_e = число полезных событий, prerequisites которых станут выполнены
H_e = (completed_similar + 1) /
      (completed_similar + dropped_similar + no_show_similar + declined_similar + 2)
```

`similar` в политике v1 — добровольные активности того же `type` и `format` за 180 дней относительно DATA/DEMO_AS_OF. `in_progress` не включается в отрицательные исходы. При отсутствии истории H=0.5. H — сглаженный исторический сигнал, **не** обученная вероятность успеха.

No-show, declined и dropped сохраняют разные значения в evidence. Совпадение их слагаемых в формуле не разрешает объяснять их одинаковой мотивацией. Историческое `date` у self-paced ограничивает точность окна завершений; это оговорка evidence.

Примеры H: без записей 1/2; при двух completed и одном dropped — 3/5. Это арифметические примеры, не оценки конкретного сотрудника.

Нормализация в текущем пуле:

```text
N(z_e) = z_e / max(z), если max(z) > 0; иначе 0
Priority = 100 * (0.40*N(U) + 0.25*N(K) + 0.15*H + 0.10*N(E) + 0.10*N(B))
```

При равенстве — стабильный event_id. Нулевая/невалидная длительность не получает искусственно выгодный делитель. Правило обработки unknown E и длина shortlist не определены численно S-FINAL: зафиксировать их в policy config и тестах, не выдавать собственное значение за требование банка.

Priority — настраиваемая эвристика v1; веса и версия хранятся в конфигурации. Это не рейтинг сотрудника. B не считает self-loop, недопустимую аудиторию, недоступные даты и повторные завершения. Подготовительный шаг с U=0 может быть полезен, если открывает достижимую полезную цепочку.

## 4. Evidence bundle

Передавать только нужные для одного сотрудника сведения: текущую роль/грейд, выбранную цель, требования, критические gaps, обобщённую релевантную историю, допустимых кандидатов, эффекты и блокеры.

Проектная структура факта для реализации:

```json
{
  "evidence_id": "fact:example:gap:system_design",
  "kind": "skill_gap",
  "source_type": "computed_domain_fact",
  "source_refs": ["baseline_version", "target_profile_version"],
  "value": {"current": 2, "required": 4, "gap": 2}
}
```

Это пример контракта, не реальная запись API. References должны разрешаться на фактические версии/records. Сами IDs не доказывают правдивость reason: сервер/рендерер должен предотвращать ложные числа и неподдержанные выводы в объяснении.

Стремиться показать четыре группы: `grade`, `skill_gap`, `history`, `target_requirements`. Минимум три фактора по ТЗ. Когда история отсутствует, это явно указанный контекст, а не выдуманные успешные курсы; пустой factor label без содержательного факта не считается объяснением.

Не писать «завершено в срок», когда нет достоверного completed_at и due_date. Не писать «ленивый», «ненадёжный» и другие психологические ярлыки. Нужны короткие доказуемые основания, не скрытые рассуждения модели.

## 5. Ответ модели и повторная проверка

Базовый контракт S-FINAL:

```json
{
  "recommendations": [{
    "event_id": "существующий ID из переданного пула",
    "reason": "краткое обоснование",
    "factor_keys": ["grade", "skill_gap", "history", "target_requirements"],
    "evidence_ids": ["ID проверенных фактов"],
    "alternative_event_id": null,
    "alternative_reason": "сравнение или причина отсутствия альтернативы"
  }],
  "warnings": []
}
```

В [машиночитаемом schema-файле](contracts/recommendation.schema.json) приведён **model-neutral проектный контракт**, а не обещание поддержки конкретным SDK/провайдером. Адаптер должен использовать реально поддерживаемый способ структурированного ответа и проверить его минимальным live запросом.

После ответа проверить: 1–3 уникальных выбора при непустом candidate pool, существование ID, актуальную eligibility, factor/evidence references, допустимые поля, корректность сравнения. Side quest ID не должен маскироваться под catalog event_id. Продолжение существующего участия разрешается сервером по текущему состоянию.

Числа before/after отображать из domain-расчёта. Структурно валидный JSON может содержать содержательно неверное утверждение; schema сама по себе не подтверждает reasoning.

При пустом candidate pool не заставлять модель выбрать событие: сервер возвращает отдельное объяснимое состояние. При ошибке ответа — максимум одна ограниченная попытка исправления, только если остаётся общий latency budget.

## 6. Режимы ответа

| Mode | Что означает | Что нельзя утверждать |
|---|---|---|
| `live_ai` | Проверенный результат реального вызова для актуальных facts | Что схема гарантирует правильность всех фраз. |
| `cached_live_ai` | Ранее полученный live ответ для того же согласованного cache key | Что вызов выполнен сейчас. |
| `rules_fallback` | Детерминированный результат при недоступности/ошибке AI | Что новая рекомендация создана моделью. |
| `demo_fixture` | Маркированная демонстрационная заготовка | Что это live inference на новом профиле. |
| `unavailable` | Рекомендация недоступна | Что техническая ошибка означает catalog gap. |

UI должен показывать mode, дату и актуальность. Детальные technical identifiers можно оставить в inspector/evidence, не перегружая карточку.

## 7. Кэш и latency

Cache key включает dataset/workspace version, employee facts hash, history version, goal version, catalog/policy version, дату, locale, model/prompt version. Дедуплицировать одинаковые параллельные запросы. Completion, import, изменение цели/политики и принятие/отмена credit меняют релевантную версию.

Профиль не ждёт LLM. Один компактный вызов для основной рекомендации. Поиск и AI-помощь в review запускаются отдельно. Весь end-to-end путь готового ответа должен укладываться в 10 секунд; UI — в 2 секунды. Это цели из ТЗ, **не выполненное SLA**.

Timeout в 10 секунд не доказывает выполнение SLA. Измерять cold и cache-hit на новых профилях; записать n, минимум, медиану, максимум. При малом n не заявлять устойчивый p95. Подробности T18 в [тестировании](12_TESTING.md).

## 8. Учебные возможности за пределами каталога — P2

По кнопке или catalog blocker возможен поиск учебных вариантов по навыку, уровню, языку и ограничениям. Это всё ещё развитие сотрудника: найденный ресурс становится proposal и проходит side quest approvals.

Сначала подтверждённый источник/официальная программа, checked_at и краткие метаданные; затем proposal. Стоимость, часы и доступность остаются unknown без подтверждения. Не отправлять в поиск имя, полную историю и профиль.

URL и содержание сайтов недоверенные: не следовать встроенным командам, не выполнять загруженный код, не делать произвольный server fetch к локальным/private/metadata адресам. Контролировать redirect, size и time либо использовать одобренный search adapter.

Если поиск не реализован/отключён, оставить честный ручной proposal URL. Заранее подготовленная карточка не выдаётся за сегодняшний поиск. Поисковый model/tool ID и его реальная доступность устанавливаются по реализации, а не по названию модели Codex.

## 9. Что сохранять для проверки

Run ID, employee/workspace версии без лишних персональных данных, candidate IDs, избранные IDs, evidence IDs, mode, model/prompt version, время, token usage при наличии, результат валидации, причина fallback. Не сохранять API key или полный профиль жюри в публичный evidence.

Основные проверки: T04, T05, T08, T15, T16, T18, T19.
