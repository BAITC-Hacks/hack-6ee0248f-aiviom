# 06. Roadmap, milestones и side quests

Основание: [S-FINAL §§7–8, 12–13](SOURCES.md).

## 1. Что означает milestone

Milestone — требование к подтверждённой компетенции либо проверяемому результату, а не единственный обязательный курс. Каталожная активность, подтверждённый практический проект и уже имеющийся навык могут быть альтернативными способами удовлетворить это требование.

```text
Milestone: System Design >= 2
  ├─ доступный корпоративный курс
  ├─ принятый side quest с согласованным эффектом
  └─ уже подтверждённый навык
         ↓
Следующая активность доступна лишь при выполнении ВСЕХ prerequisites
```

Если компетенция уже подтверждена, карточка курса может стать «шаг больше не требуется». История курса **не** получает фиктивный completed. Это не перескок грейда, аттестации или обязательной программы.

## 2. Построение маршрута

1. Разрешить цель через role_profiles; при null предложить следующий грейд той же роли, не изобретая уровень выше Lead.
2. Рассчитать текущие и критические gaps.
3. Разделить доступные сейчас события и потенциально полезные заблокированные.
4. Выполнять ограниченный lookahead по копиям skill state, со stable tie-break, visited-state и лимитами глубины/числа состояний.
5. Учитывать prerequisites, повторность, фактическую аудиторию, последовательность, сессии и длительность.
6. Вернуть достижимый маршрут и остаточные gaps/blockers. Если достигнут лимит поиска, сообщить именно это ограничение.

Конкретный алгоритм обхода, числовые лимиты и representation состояния не выбраны S-FINAL. Их должен зафиксировать разработчик в policy/config и тестах. Нельзя документировать ограниченный поиск как доказательство отсутствия любого возможного маршрута.

При прогнозе не повышать фактический grade ради audience. Событие для Senior остаётся условным до кадрового подтверждения Senior. Непринятый side quest не открывает реальные prerequisites.

## 3. Состояния узла

| Состояние | Смысл |
|---|---|
| `met` | Условия компетенции подтверждены текущим state. |
| `available` | Следующее действие допустимо сейчас. |
| `planned` | Выбрано в план. |
| `in_progress` | Есть текущее выполнение. |
| `awaiting_approval` | Ожидается обязательное согласование. |
| `blocked` | Есть конкретный blocker. |

Preview — отдельное simulated представление, не один из способов записать реальные met/credits. Смена цели создаёт новую версию плана, сохраняя старую историю и награды.

## 4. Содержание side quest

| Группа | Сведения |
|---|---|
| Идентичность | ID, автор, workspace, цель/plan version, название. |
| Предложение | Описание, source/URL при наличии, deliverables, часы/стоимость или unknown. |
| Обучающий эффект | Предложенные skill IDs, prerequisites, критерии проверки. |
| Контроль | Риски/доступы, rule version, согласования, причины решений. |
| Результат | Доказательства, статусы, audit, accepted credit ID. |

Ручное предложение и автоматически найденная возможность проходят один процесс. Найденное предложение начинается как `discovered`, а не «одобрено компанией».

## 5. Жизненный цикл

```text
draft/discovered → submitted → advisor_review
    → needs_revision / rejected
    → approved
    → resource_review, если нужны время/расходы
    → policy_review, если нужна новая эквивалентность
    → ready → in_progress → evidence_submitted
    → accepted / needs_revision / rejected
```

Resource и policy approvals могут идти параллельно. `ready` разрешён только после всех необходимых согласований. Для обычной заявки по утверждённой политике достаточно advisor; пять подписей по умолчанию не требуются.

Надпись `approved` означает согласование предложения, а не подтверждение результата. Представление параллельных approvals в БД (отдельные records/flags) — задача реализации. UI должен различать причины `needs_revision` на этапе предложения и на этапе проверки доказательств.

## 6. Матрица решений

| Переход/действие | Кто | Обязательная проверка | Результат |
|---|---|---|---|
| Создать/отправить | Сотрудник | Своя заявка и цель, валидные ссылки | Submitted, без gain. |
| Проверить предложение | Назначенный advisor | Не собственная работа, существующие skills/rule | Критерии, конкретные gain/cap, причина решения. |
| Согласовать ресурс | Менеджер в scope | Реальные часы/расходы и полномочия | Resource approval, без gain. |
| Утвердить новое правило | Супервайзер | Версия правила, основания и конфликт интересов | Policy decision, без изменения исходного grade requirements. |
| Начать | Автор | Все необходимые approvals получены | In_progress. |
| Подать доказательство | Автор | Допустимое состояние, safe evidence | Evidence_submitted. |
| Принять результат | Уполномоченный advisor | Критерии выполнены, не self-approval | Accepted, один credit и последующий пересчёт. |
| Вернуть/отклонить | Уполномоченный reviewer | Обязательная причина | Needs_revision/rejected, без gain. |

Супервайзер контролирует правила и эскалации. Нельзя автоматически считать его полномочия правом произвольно начислять любой навык любому сотруднику.

## 7. Правило зачёта

До выполнения advisor фиксирует конкретные skill IDs, `gain`, `max_level <= 5` и критерии принятия. Нет универсального «любой проект = +2».

После `accepted` транзакционно связать decision, completion/skill ledger, reward ledger по согласованной политике, audit и изменение версии кэша. Approval предложения даёт 0 skill gain и 0 XP.

Один credit ID запрещает повторное начисление. Повторное использование одинакового доказательства обнаруживается и требует отдельного обоснования; совпадение URL не должно незаметно дать второй зачёт.

## 8. Исправления и отмена

Accepted decision нельзя незаметно отредактировать. Исправление — отдельная аудируемая отмена с причиной и соответствующими правами. Recompute идёт от baseline по активным credits; gain не вычитается арифметически из текущего capped уровня.

Если reward уже потрачен, отмена создаёт review/audit case. Не скрывать несоответствие отрицательным балансом либо удалением истории.

## 9. Безопасность доказательств

В первой версии достаточно текста и безопасной ссылки. Файловые доказательства — только если реализованы ограничения типа/размера и безопасное хранение. Загруженные программы не выполняются. AI-замечание к работе — совет reviewer, не принятие результата.

Секретные клиентские данные, реальные персональные данные и credentials не должны становиться публичным доказательством навыка. Видимость evidence следует role scope, а не доступности кнопки в UI.
