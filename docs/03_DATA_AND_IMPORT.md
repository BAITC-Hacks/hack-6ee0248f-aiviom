# 03. Данные, время и импорт

Основание: [S-FINAL §9 и S-KIT](SOURCES.md). Поля и CSV-заголовок ниже дополнительно сверены с доступной копией архива. Это проверка исходных файлов, а не тест работающего импортера.

## 1. Версия исходного набора

| Файл | Верхний уровень | Исходный объём |
|---|---|---:|
| `employees.json` | `{meta, employees: [...]}` | 200 |
| `events.json` | `{meta, events: [...]}` | 40 |
| `skills.json` | `{meta, proficiency_scale, skills: [...], role_profiles: [...]}` | 60 навыков; 32 role profiles |
| `activity_history.csv` | CSV с заголовком | 2 743 записи |

В доступной копии путь — `case_1/career_quest_dataset/`. `meta` содержит `dataset`, `version`, `as_of_date`; версия `1.0`, дата `2026-10-01`.

**Обнаружено расхождение checksum:** доступный архив имеет тот же размер 64 298 bytes и проходит CRC-проверку, но его SHA-256 отличается от указанного в S-FINAL. Значения и границы вывода сохранены в [отчёте инспекции](DATASET_INSPECTION.md). Нельзя объявлять файл повреждённым или побайтово тождественным версии спецификации без дополнительной проверки. Для релиза указать фактически используемый checksum.

Числа 200/40/60/32/2743 проверяются для **оригинального seed**, а не для всей БД после добавления extensions и профилей жюри. Эти числа не должны быть hard limits импортера.

## 2. Канонические поля

### 2.1. Профиль сотрудника

| Поле | Тип и смысл |
|---|---|
| `employee_id` | Стабильный string ID. Не ограничивать допустимые новые IDs исходными E0001…E0200. |
| `full_name`, `department` | Строки; в исходном наборе имена вымышлены. |
| `role`, `grade` | Текущие роль/грейд; пара соответствует `role_profiles`. |
| `manager_id` | ID руководителя либо null; организация менеджерского scope. |
| `hire_date` | Дата найма. |
| `tenure_months` | Целое число полных месяцев на дату среза. |
| `work_format` | `office`, `hybrid`, `remote`. |
| `preferred_language` | `kk`, `ru`, `en`. |
| `career_goal` | `{target_role, target_grade}` либо null. |
| `skills` | Объект `skill_id → уровень 0–5`; отсутствующий навык = 0. |
| `last_review_date` | Дата baseline-оценки навыков. |

`career_goal` не меняет текущие `role`/`grade`. У исходного seed manager — Lead того же отдела; для дополнительных профилей S-FINAL допускает unresolved manager с предупреждением, без выдумывания руководителя и без блокировки самого skill analysis.

### 2.2. Навыки и требования

`skills[]`: `skill_id`, `name`, `type` (`hard`/`soft`), `category`, `description`.

`role_profiles[]`: `role`, `grade`, `required_skills` (`skill_id → минимальный уровень`), `critical_skills` (массив IDs). Порядок грейдов: Junior → Middle → Senior → Lead. Критический навык — часть требований, а не дополнительный неограниченный бонус к Coverage.

`proficiency_scale` описывает уровни 0–5. Не заменять порядковые уровни вероятностью успеха или процентом человеческой эффективности.

### 2.3. События

| Поле | Тип и смысл |
|---|---|
| `event_id`, `title`, `description` | ID и описание каталожного события. |
| `type` | `compliance`, `onboarding`, `course`, `workshop`, `mentoring`, `certification`, `meetup`. |
| `format` | `online`, `offline`, `self_paced`. |
| `duration_hours` | Общие трудозатраты, не автоматически длительность одной сессии. |
| `mandatory` | Обязательное HR-назначение; не кандидат добровольной AI-рекомендации. |
| `target_roles`, `target_grades` | Аудитория нового участия. |
| `develops_skills` | Массив `{skill_id, gain, max_level}`. |
| `prerequisites` | Объект `skill_id → необходимый уровень`. |
| `upcoming_sessions` | Массив дат; пустой у доступного без расписания `self_paced`. |

Обязательность не означает автоматически отсутствие gain. Комплаенс в китe не развивает навыки, а обязательный onboarding содержит реальные эффекты. Применять фактический `develops_skills`, но держать назначения отдельно от добровольных рекомендаций.

### 2.4. История

Точный заголовок исходного CSV:

```csv
record_id,employee_id,event_id,date,due_date,status,completion_pct,score,feedback_rating,assigned_by
```

| Поле | Правило |
|---|---|
| `record_id` | Уникальный ID участия. |
| `employee_id`, `event_id` | Ссылки на профиль и событие. |
| `date` | Дата сессии; у self-paced — зачисление/назначение, не точное completed_at. |
| `due_date` | Дата либо пусто; в исходном наборе для обязательных мероприятий. |
| `status` | Один из перечисленных ниже статусов. |
| `completion_pct` | Целое 0–100; не коэффициент skill gain. |
| `score` | Целое 0–100 либо пусто; не вводить дополнительный проходной порог. |
| `feedback_rating` | Целое 1–5 либо пусто. |
| `assigned_by` | `self`, `manager`, `hr`. |

| Статус | Смысл | Skill gain |
|---|---|---|
| `completed` | Завершено, completion_pct=100 | По review cutoff и правилам события. |
| `in_progress` | Выполняется | Нет; можно предложить продолжение. |
| `dropped` | Начато и прекращено | Нет. |
| `no_show` | Неявка на scheduled session | Нет; не выводить оценку личности. |
| `declined` | Отказ от назначения руководителя/HR | Нет; не смешивать с самостоятельным dropout. |
| `overdue` | Обязательное не завершено к due_date | Нет. |

Пустые ячейки в nullable полях нормализовать в null, а не в 0, пустую дату или NaN. Проверять диапазоны и допустимые сочетания полей. Не проверять историческое участие только по сегодняшней аудитории: оно могло относиться к предыдущему грейду.

## 3. Три времени

| Время | Назначение |
|---|---|
| `REAL_NOW` | Реальные часы для audit, возраста заявки и действий пользователей; явно учитывать timezone. |
| `DATA_AS_OF` | `2026-10-01` — исходная доменная дата набора. |
| `DEMO_AS_OF` | Управляемая, явно видимая дата конкретного demo workspace. |

История исходного набора: `2024-10-01`…`2026-09-30`. Операции демо с будущими scheduled sessions должны использовать честно отображаемый `DEMO_AS_OF`; нельзя незаметно двигать системные часы или глобальную дату всех пользователей.

Для новых завершений хранить реальный `created_at` и отдельный доменный `completed_at`. Точность и timezone нового timestamp должны быть частью фактической DB/API schema.

## 4. Historical replay

Базовые `skills` соответствуют `last_review_date`. Учитывать completed **после**, а не до или на этой дате. Если надёжного `completed_at` нет, политика S-FINAL использует историческое `date` как proxy, с `completion_time_quality=proxy`.

Это не доказывает фактическую дату завершения self-paced курса. Курс мог быть начат до аттестации, а завершён после неё. Ограничение должно быть видно в provenance, аналитике и README.

Порядок replay: `(effective_completed_at, stable_record_id)`. К одинаковому baseline не добавлять повторно уже вычисленные gains. Подробности и примеры: [domain calculations](04_DOMAIN_CALCULATIONS.md).

## 5. Pipeline импорта

```text
Выбор JSON/CSV/ZIP
    → безопасное чтение
    → нормализация документированного wrapper
    → schema validation
    → referential checks для всего пакета
    → preview и отчёт
    → подтверждение HR/evaluator
    → атомарная запись import batch
    → recompute затронутых сотрудников
    → повышение версий / invalidation cache
```

ZIP: игнорировать `__MACOSX`, `.DS_Store`, `._*`; запретить path traversal и выход из целевой директории. Лимиты количества, размера и распаковки — обязательные фактические настройки для документирования, но их числовые значения в S-FINAL не заданы.

Основные входы — реальные wrappers и CSV. Поддержка bare array и одиночного профиля возможна как дополнительная явно документированная нормализация, но не заменяет поддержку исходного формата.

Новые профили и история импортируются без повторной загрузки всего каталога. Сначала рассмотреть связанные профили одного пакета, затем проверять manager references. Неизвестный `skill_id`/`event_id` нельзя использовать для зачёта без валидного каталога.

## 6. Дубли, конфликты, атомарность

| Случай | Поведение |
|---|---|
| Тот же record_id и те же данные | No-op, без дополнительного credit. |
| Тот же record_id с другим содержимым | Явный conflict; не скрытый overwrite. |
| Новые связанные профили | Проверка ссылок после нормализации всего пакета. |
| Неизвестный manager | Warning и unresolved relation; не даёт менеджерских прав. |
| Невалидный skill/event reference | Ошибка для начисления/зависимых записей; фиктивный объект не создаётся. |
| Ошибка в подтверждаемом атомарном пакете | Нет частично применённых мутаций. |

Preview должен показывать planned accepted/rejected/no-op/conflicts по строкам и полям. Частичный импорт возможен только как отдельно согласованная явная операция над валидным подмножеством; исходная спецификация не разрешает незаметную частичную запись.

Политика обновления существующего employee baseline требует явного versioning: новая аттестация не должна добавляться поверх старых агрегированных skills. До реализации такого режима не выдавать insert-only импорт за поддержку любых updates.
