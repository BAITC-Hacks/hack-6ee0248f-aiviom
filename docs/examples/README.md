# Документационные примеры импорта

Это искусственные fixtures для проверки формата, а не профили заказчика или жюри. Идентификаторы имеют префикс `DOC_`. Файлы:

- [Профиль](jury_employee.example.json) — новый Middle Backend Engineer с целью Senior.
- [История](jury_history.example.csv) — одна синтетическая завершённая активность после review.

Требуется исходный каталог с `EV_005`, нужными навыками и role_profiles. `manager_id=E0050` ссылается на исходный seed; если менеджер отсутствует в другом workspace, ожидается документированный unresolved warning, а не выдуманный руководитель. Историческая дата участия не обязана входить в сегодняшние `upcoming_sessions`.

## Ожидаемая проверка по правилам, не результат запуска

1. Импортировать профиль и историю одним preview/commit.
2. Baseline System Design=2, API Design=2. `EV_005` в доступном китe даёт по +1 с cap=3. При review cutoff на 01.09.2026 и участии 20.09.2026 effective значения должны стать 3 и 3.
3. `EV_005` уже completed и не должен снова предлагаться как новая активность.
4. Остальные отсутствующие skills трактуются как 0. Не предполагать, что это полный assessed skill inventory сотрудника.
5. Повторно импортировать тот же пакет: новые history/skill/reward записи не появляются.
6. Запросить live рекомендацию на новом ID и проверить evidence. Нельзя использовать заготовленный ответ для `DOC_EMPLOYEE_001`.

Работа импортера с этими файлами ещё не проверена: статус `NOT_RUN`. Фактический importer может потребовать исправления несоответствий заявленной схеме; сами примеры не доказывают готовность API.
