# 02. Архитектура и взаимодействие компонентов

> Статус: проектные материалы. Фактический запуск и результаты текущей реализации см. в [README](../README.md), [ACCEPTANCE](ACCEPTANCE.md), [FORMULAS](FORMULAS.md) и [DEMO_API](DEMO_API.md). Непроверенные положения ниже не являются заявлением о готовности.

Основание: [S-FINAL §§5, 9–11, 15–18](SOURCES.md).

## 1. Архитектурный стиль

Целевой вариант — **простой модульный монолит** с реляционным хранилищем и внешним адаптером LLM. Модули отделяются ответственностью и контрактами, а не обязательно отдельными процессами.

В S-FINAL для пустого репозитория предложен TypeScript full-stack с React и SQLite. Framework и ORM не зафиксированы. Рабочий стек не следует менять ради этого предложения. Фактические runtime, package manager, framework, DB, ORM и версии определяются по коду и заносятся в [паспорт релиза](RELEASE_MANIFEST.json).

```text
Browser: employee / advisor / manager / HR / supervisor
                             │
                    Session + workspace scope
                             │
                     Application API
        ┌────────────────────┼────────────────────┐
        │                    │                    │
 Data / import         Domain engine        Workflow / policy
 fixtures, review      skills, gaps,         plans, approvals,
 history, catalog      eligibility,         completion, help,
                       roadmap, preview     credits, rewards
        │                    │                    │
        └────────────────────┼────────────────────┘
                             │
                 Relational DB + audit + versions
                             │
               Recommendation orchestration
                evidence → LLM → validation
                             │
                   Approved provider / gateway
```

Учебный поиск P2 — отдельная операция по запросу, а не обязательный шаг каждого построения рекомендации.

## 2. Границы ответственности

| Модуль | Вход | Выход и ответственность | Чего не делает |
|---|---|---|---|
| Session/access | Установленная identity и workspace | Разрешённые роли, субъект и scope | Не доверяет роли из произвольного body. |
| Import | Исходные JSON/CSV/ZIP и текущая версия | Валидация, preview, manifest, атомарная запись | Не переписывает исходный кит. |
| Skill state | Review baseline и активные учитываемые credits | Effective skills с provenance | Не начисляет к уже агрегированному state повторно. |
| Goal/gaps | Цель, role_profiles, effective skills | Gap, Coverage, CriticalMet, plan baseline | Не утверждает кадровое повышение. |
| Eligibility | Состояние, история, аудитория, prerequisites, дата | Допуск или явные блокеры | Не заменяет фактический grade целевым. |
| Roadmap/preview | Требования, кандидаты, policy, бюджет | Маршрут, альтернативы, simulated state | Не пишет projected gains в реальные skills. |
| Recommendation | Проверенный fact bundle и кандидаты | Выбор LLM, валидированный ответ, mode/version | Не меняет правила допуска и начисления. |
| Completion/quests | Авторизованное подтверждение результата | Completion, skill/reward ledger, audit | Не принимает результат самим его автором. |
| Analytics | Разрешённый scope, период, доменная дата | Агрегаты с числителем/знаменателем | Не ранжирует людей по ценности. |
| UI | Готовые domain/API значения | Экраны, evidence и действия | Не имеет второй независимой версии формул. |

## 3. Три состояния навыков

`review baseline` — зафиксированная оценка; `effective skills` — baseline плюс учитываемые завершения и активные credits; `projected skills` — результат симуляции потенциальных действий. Их происхождение различается в API и UI.

Хранить либо воспроизводимый вычисленный snapshot с версиями, либо вычислять его по запросу. Выбор способа материализации — решение реализации. В обоих случаях истинность навыков должна восстанавливаться из baseline и активных credits в стабильном порядке.

## 4. Поток рекомендации

1. Сервер проверяет scope сотрудника.
2. Получает согласованные версии baseline, history, goal, catalog и policy.
3. Вычисляет effective skills, gaps и кандидатов; профиль можно показать до окончания LLM-вызова.
4. Создаёт compact evidence bundle; выполняет один основной запрос модели.
5. Валидирует IDs, допуск, уникальность и evidence references.
6. Пишет recommendation run с mode, версиями и безопасной технической статистикой.
7. Возвращает пользователю проверенные шаги либо честный fallback/error.

Если facts изменились во время внешнего вызова, ответ нельзя выдать как актуальный без проверки версии. Конкретный способ — отклонить устаревший ответ или пересчитать при наличии budget — должен быть зафиксирован разработчиком.

## 5. Поток изменения состояния

Выполнение и accepted side quest должны логически связывать:

```text
Проверка scope и версии
    → проверка уникальности действия
    → completion / accepted decision
    → skill credit
    → reward credit по утверждённой политике
    → audit event
    → новая версия состояния
    → invalidation recommendation cache
```

Записи в одной БД связываются транзакцией. Если кэш отдельный, повышение версии в той же транзакции и включение версии в cache key не дают обслужить старый ответ как новый. Способ доставки invalidation после commit должен быть устойчив к повтору и описан по факту кода.

Длительный LLM/поисковый запрос не должен быть условием удержания открытой транзакции начисления. Конкретные transaction boundaries проверяются в API/storage и тестах.

## 6. Идентичность, версии и изоляция

Каждая пользовательская сущность и запрос ограничены workspace. Версии нужны для employee facts, history, goal/plan, catalog/policy и модели/prompt. Смена цели создаёт новую baseline version плана, а не удаляет прошлую историю.

Новый demo workspace получает воспроизводимый seed и собственные mutations. Reset одного workspace не затрагивает другого. У нескольких dev workers отдельные DB/ports/temp artifacts.

## 7. Основные инварианты

| Инвариант | Где обеспечивается |
|---|---|
| Нет навыков ниже 0 или выше 5; низкий cap не снижает текущий навык | Domain + input validation + T06. |
| Один результат не начисляется дважды | Unique constraints, idempotency, transaction + T09/T10/T17. |
| Preview ничего не начисляет | Отдельный simulated state + T12. |
| Неавторизованное чтение/изменение отклоняется | Server-side scope + T13. |
| LLM не может выбрать недопустимую активность | Candidate builder + output validator + T15. |
| Исторический seed не является живым результатом AI | Mode/provenance + T15/T19. |
| Аналитика и карточка сотрудника согласованы | Общая domain-логика + T14/T16. |

## 8. Deployment и инструменты разработки

Hosted demo дополняет локальную воспроизводимость. Judge gateway не должен быть произвольным proxy к модели: только разрешённые операции приложения, с scope и бюджетом.

Codex и локальный `impeccable` относятся к разработке. Наличие этих инструментов у эксперта не должно быть условием запуска продукта. Их фактическое использование раскрывается в [сторонних компонентах](THIRD_PARTY.md), но не изображается продуктовой AI-функцией.
