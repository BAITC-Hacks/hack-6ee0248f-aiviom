# 13. Руководство независимого проверяющего

Основание: [S-FINAL §§16, 20–22](SOURCES.md). Назначение — проверить поведение выбранного commit, а не пересказать идею.

## 1. Перед началом

Открыть [паспорт релиза](RELEASE_MANIFEST.json). Должны быть известны tested SHA, actual commands, URL, demo identities, источник seed и независимый live AI access. В текущем комплекте эти application-параметры ещё не установлены: выполнение сценариев требует заполнения и проверки по коду.

Выполнить [clean deployment](11_DEPLOYMENT.md). Зафиксировать commit, время, DATA/DEMO_AS_OF, workspace и AI mode. Не использовать credentials разработчика, которых нет в предусмотренном маршруте проверки.

Выбор demo identity в разрешённой sandbox не означает production authentication. Для API/security тестов проверять реальный server-side scope и невозможность выйти за workspace.

## 2. Сценарий A — профиль и объяснимый следующий шаг

| Шаг | Действие | Ожидаемое наблюдение |
|---|---|---|
| A1 | Открыть сотрудника из заполненного demo | Текущие role/grade, цель, baseline/effective skills, история и маршрут. |
| A2 | Посмотреть Coverage, CriticalMet, Progress | Разные индикаторы; знаменатель/основание понятны, нет обещания повышения. |
| A3 | Запросить рекомендацию | До трёх реальных допустимых шагов; честный mode. |
| A4 | Открыть explanation/evidence | Минимум три фактора, конкретные gap/requirements/history факты. |
| A5 | Открыть «почему не другое» | Сравнение реальной альтернативы либо объяснение её отсутствия. |
| A6 | Проверить prerequisites, аудиторию, gain/cap и history | Выбор не нарушает hard constraints, не повторяет completed без разрешённого исключения. |

В сценарии со слабейшим некритичным навыком проверить, учитывает ли система критическую цель и историю. Нельзя судить качество только по красивому тексту.

## 3. Сценарий B — preview и подтверждённый прогресс

1. Зафиксировать реальные skills, history count, plan version, credits и баланс.
2. Выполнить preview одного допустимого события. Проверить before/after и Coverage impact по [формуле](04_DOMAIN_CALCULATIONS.md).
3. Обновить страницу: реальный state после preview не изменился.
4. Выполнить разрешённое demo completion; для scheduled event использовать честно установленную допустимую DEMO_AS_OF или подготовленный сценарий, не фальсифицируя реальные timestamps.
5. Проверить ровно один credit, изменение effective skills/roadmap, актуальную рекомендацию и HR view.
6. Повторить тот же запрос/действие: дополнительный gain/XP не появляется.
7. Перезапустить приложение по README: изменения сохранились.

Если cap не даёт прироста, корректный результат может быть delta=0. Не выбирать заведомо бессмысленный пример для доказательства «сдвига навыка»: demo seed должен содержать событие с реальным ожидаемым эффектом.

## 4. Сценарий C — side quest и пять ролей

| Роль | Действие | Что проверить |
|---|---|---|
| Сотрудник | Подать предложение с deliverables и навыками | Submitted, без начисления. |
| Advisor | Проверить цель, критерии, gain/cap; согласовать | Proposal approved, навыки ещё прежние. |
| Менеджер | Согласовать ресурс, если он действительно нужен | Ресурсное решение, не кадровый/skill credit. |
| Супервайзер | Рассмотреть новое правило/эскалацию, если оно требуется | Причина и версия policy, нет скрытого изменения grade requirements. |
| Сотрудник | Подать доказательства выполнения | Evidence_submitted. |
| Advisor | Принять подготовленный проверяемый результат | Один accepted credit; запрет self-approval; новый milestone/route. |
| HR | Открыть связанный агрегат/журнал | Согласованное изменение данных в разрешённом scope. |

Для обычной заявки по действующей политике менеджер и супервайзер могут не потребоваться. Для демонстрации их экранов использовать отдельные заполненные cases, не добавлять пять обязательных подписей в каждый workflow.

Проверить также отклонение/доработку с причиной. Approved и accepted должны оставаться различимыми.

## 5. Сценарий D — HR и помощь

Открыть gap table, participation distribution, no-next-step и mandatory overdue. Для хотя бы одного показателя раскрыть numerator/denominator и сверить на малом fixture. Проверить отсутствие NaN при нулевом знаменателе.

Открыть catalog gap: система должна объяснить, чего именно не хватает — аудитории, prerequisite, сессии, предложения либо согласования. LLM outage не превращается в catalog gap. Ограничение поиска обозначается отдельно.

Открыть сотрудника с mandatory назначением и запросом помощи. Нет deadline — нет выдуманной просрочки. Обязательный комплаенс без effects не создаёт фиктивный skill gain. Награды за mandatory проверяются только после разрешения CQ-OPEN-01.

## 6. Сценарий E — новый импорт

Дать HR/evaluator новые JSON/CSV в формате набора. Для открытого примера доступны [профиль и история](examples/README.md); жюри вправе использовать собственные данные в той же схеме.

Проверить preview, указание counts/warnings/errors, atomic commit и появление нового employee ID. Затем открыть профиль и запросить **новый live AI ответ**. Seed fixture, cached ответ на другого человека и rules fallback не доказывают эту проверку.

Повторить идентичный import: no-op. Изменить содержимое того же record ID: ожидается явный conflict. Неизвестный manager может дать warning; неизвестные skills/events не дают фиктивного зачёта.

Для документационного примера ожидается System Design 2→3 и API Design 2→3 после исторического `EV_005`; это ожидание по source rules, не заранее выполненный тест.

## 7. Сценарий F — права и отказоустойчивость

Попробовать прямой API-доступ к чужому профилю/заявке, import от employee, self-approval и другой workspace. Проверить серверный отказ без эффекта. Названия actual routes/status codes брать из релизного API, а не угадывать.

В контролируемом тесте отключить provider/использовать ошибочный ответ: видны fallback/error и соответствующий mode, профиль остаётся доступным. Не изменять действительный секрет в публичном демонстрационном окружении для такой проверки — использовать предусмотренный test setup.

## 8. Что зафиксировать

[Матрица приёмки](ACCEPTANCE.md): PASS/FAIL/NOT_RUN для выполненных сценариев, actual commit, environment и evidence. Для latency — отдельные cold/cache-hit замеры. Для неготовой заявленной функции — честный FAIL при выполненной проверке либо NOT_RUN с причиной недоступности, а не фиктивный PASS.

Документация должна отвечать на вопрос «что сделано и как проверить». Если runtime инструкции не заполнены, это подтверждённое отсутствие необходимой части релизной документации, даже когда проектная архитектура описана подробно.
